# Фотопринт · Управленческая платформа (трек 1)

MVP «Единой системы управления компанией» для ООО «Фотопринт» (хакатон «Фабрика идей», трек 1).
Руководство видит состояние компании, причины отклонений и ответственных в одном окне:
план/факт/прогноз 16 KPI → детализация до участка, продукта, кампании, заказа → карточка решения → журнал.

## Быстрый запуск (≈1 минута, ОТ-01)

Нужен только Python 3.10+ (внешних зависимостей нет).

```bash
cd fotoprint
python3 server.py
```

Откройте http://localhost:8080. При первом запуске (и каждый новый день) сервер сам генерирует свежий синтетический набор данных.
Порт можно сменить: `PORT=9000 python3 server.py`.

### ИИ-ассистент «Фотик»

Кнопка с Фотиком в правом нижнем углу открывает чат с аналитиком дашборда. Чтобы он отвечал, запустите сервер с ключом Claude API:

```bash
ANTHROPIC_API_KEY=sk-ant-... python3 server.py
```

Ключ читается только сервером из окружения: на фронтенд, в ответы API и в журнал он не попадает. Без ключа дашборд работает как обычно, а Фотик вежливо сообщает, что не подключён. Модель можно сменить: `FOTIK_MODEL=… python3 server.py` (по умолчанию `claude-sonnet-5-5`).

Как он устроен:
* перед каждым вопросом сервер собирает снимок дашборда с учётом фильтров и прав пользователя (`fotik_context`): выбранные период, подразделение, продукт и даты; все KPI с планом, фактом, прогнозом и статусом (закрытые — без значений); график с экрана; загрузку участков; недельные агрегаты за 8 недель вместо дневных рядов; сравнение «неделя к неделе»; аномальные дни (|z| ≥ 2,5 после поправки на день недели); свежесть источников; прогноз мощности на 6 недель;
* прогнозы считаются в коде (`fotik_trend`): линейная регрессия по 56 полным дням с профилем дня недели, скользящие средние 7 и 28 дней, сумма на 30 дней вперёд и до конца месяца с 80-% диапазоном. Модель получает эти числа и допущения и не придумывает свои;
* быстрые вопросы: «Что изменилось за неделю?», «Есть ли аномалии?», «Прогноз на месяц»; переписка хранится во вкладке до выхода из системы;
* ограничение — 20 вопросов в минуту на пользователя; каждый вопрос пишется в журнал (без текста вопроса и без ключа).

Посмотреть, какие именно данные получает Фотик: `GET /api/fotik/context?period=…&dept=…&product=…`.

### Тестовые учётные записи (пароль у всех `demo2026`)

| Логин | Роль | Что видит |
|---|---|---|
| `director` | Директор | Все экраны и все KPI (включая закрытые), создаёт и меняет решения, комментирует KPI и назначает ответственных, качество данных, журнал |
| `prod` | Руководитель производства | Только дашборд своего подразделения: «Производство и качество» и «Прогноз мощности», KPI производства (включая закрытые). Пульса, финансов, реестра решений нет |
| `sales` | Руководитель продаж и маркетинга | Только «Продажи и клиенты» и KPI продаж (включая закрытые) |
| `analyst` | Аналитик / администратор | Все KPI, качество данных, сверка, журнал; реестр решений — только чтение |

Пароль задаётся переменной `FOTOPRINT_DEMO_PASSWORD` (по умолчанию `demo2026`); в репозитории хранится только PBKDF2-хэш, секретов и ключей нет (ОТ-03).

| Требование | Где |

| Сц. 2 Провал от KPI до подразделения, заказа, продукта, кампании, причины | Клик по любому KPI → детализация («Почему так» — объяснение отклонения, разрезы с вкладом в изменение) → список заказов → сквозная карточка заказа |

## Архитектура

```
 Браузер (static/: index.html, styles.css — исходный дизайн, fotoprint.css, app.js, fotik.js/fotik.css — чат)
      │  REST/JSON, Bearer-токен
      ▼
 server.py  (http.server, стандартная библиотека)
   ├─ авторизация и роли (PBKDF2, сессии 8 ч)
   ├─ KPI-движок: items() → value_of() → план / прогноз / статус; breakdown() + explain()
   ├─ прогноз спроса и мощности, качество данных и сверка
   ├─ реестр решений (state/decisions.json, ревизии, история)
   ├─ журнал (state/audit.jsonl)
   └─ Фотик: контекст + расчётный тренд → Claude API (ключ из ANTHROPIC_API_KEY)
      ▲
 data/ (генерирует data_gen.py — имитация интеграций)
   CRM: crm_customers.json · Helpdesk: crm_tickets.json · ERP: erp_orders.json · MES: mes_production.json
   Веб-аналитика: web_analytics.json · 1С:ЗУП: zup_staff.json · 1С:Бухгалтерия: onec_finance.json · plans.json · sources.json
```

Стек: Python 3 (стандартная библиотека), ванильный JS/HTML/CSS без сборки. Дизайн-система дашборда перенесена без изменений (`static/styles.css`), новые элементы — в `static/fotoprint.css` на тех же токенах, активная палитра — исходная сине-фиолетовая (#4B56EE) из `styles.css`. Фирменная палитра picPac.by (#38524F, #DD5757, #364657, #FAF5ED) сохранена в `static/brand.css`, но не подключена; чтобы вернуть её, добавьте `<link rel="stylesheet" href="brand.css">` после `fotoprint.css` в `index.html` (и зелёные цвета пузырей в `SLOTS` в `app.js`).

Описание API — [API.md](API.md). Модель данных и допущения — [DATA.md](DATA.md). Отчёт о тестировании — [TESTING.md](TESTING.md). Сценарий демонстрации — [DEMO.md](DEMO.md).

## Тесты

```bash
python3 -m unittest discover -s tests -v
```

16 приёмочных тестов (УП-01…05, ОТ-02/05/07, доступ руководителей только к своему дашборду, комментарии и ответственные по KPI, автообновление базы и живой поток заказов, сценарии 4–5) и 4 теста Фотика (`tests/test_fotik.py`: Claude API подменяется локальной заглушкой, ключ и интернет не нужны). Поднимают сервер на свободном порту с временным каталогом состояния.

## Повторная загрузка данных

```bash
python3 data_gen.py          # перегенерировать набор (seed 2026, детерминированно)
rm -rf state                 # сбросить решения, журнал, комментарии к KPI и прочитанные уведомления
```

**Автообновление каждые 15 секунд.** Сервер раз в 15 с проверяет файлы `data/*.json` и, если какой-то изменился, перечитывает базу целиком (новый набор собирается отдельно и подменяется разом; если файл повреждён — остаются прежние данные, ошибка видна в `GET /api/health`). Открытый дашборд с той же частотой тихо подтягивает свежие цифры текущего экрана и уведомления — без анимаций появления и только когда пользователь ничего не вводит и не держит открытым окно или меню. Интервал меняется переменной: `DATA_REFRESH_SEC=60 python3 server.py`.

**Живая работа компании — у каждого сотрудника.** С тем же интервалом меняются данные всех подразделений:
* продажи (ERP, CRM, веб-аналитика) — 2–4 новых заказа (часть от новых клиентов), визиты, проекты, корзины и оплаты в воронке сайта и приложения: меняются оборот, средний чек, новые и повторные клиенты, конверсия, каналы и сегменты;
* производство (ERP, MES) — заказы проходят этапы «Принят → Модерация → Производство → Готов → Передан в доставку → Завершён», растут выпуск и очередь участков, случается брак с перепечаткой: меняются загрузка, выпуск, брак, затраты на перепечатку, lead time и очередь;
* поддержка (Helpdesk) — новые обращения с соблюдением или нарушением SLA.

Всё дописывается в `data/live_orders.json` (новые заказы, клиенты и обращения, смена этапов, выпуск и очередь участков за сегодня, воронка сайта) и переживает перезапуск; каждый заказ открывается в сквозной карточке. «Заказы в срок» считаются по заказам со сроком до вчерашнего дня, поэтому внутри дня не меняются. При генерации набора на новый день поток начинается заново. Отключить: `LIVE_SIM=0 python3 server.py`; сколько заказов поступило за день — в `GET /api/health` (`live_orders_today`).

## Известные ограничения

* Интеграции имитированы файлами JSON; расписание выгрузок моделируется (1С:Бухгалтерия намеренно «не обновлялась» 27 ч — для сценария аналитика).
* Сессии хранятся в памяти сервера: после перезапуска нужно войти снова.
* Хранилище решений — JSON-файл с блокировкой; для пилота заменить на СУБД (PostgreSQL) и вынести журнал в append-only хранилище.
* Прогноз — эвристическая модель (сезонность × кампании × очередь; мощность по численности из 1С:ЗУП), без доверительного интервала.
* Шрифт загружается с Google Fonts; без интернета используется системный шрифт.
